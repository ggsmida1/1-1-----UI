# 1-11 项目重构 — 学习笔记

> 引脚集中管理、模块拆分、头文件自包含、消除 extern 依赖

---

## 一、为什么要重构

项目写到第 10 课，`menu.c` 膨胀到 600+ 行，里面塞了时钟、菜单、秒表、手电筒、MPU6050 显示、表情包、水平仪七种逻辑。而且引脚定义散落在 6 个文件的各个角落——换一块 PCB 就要改 6 个文件，改漏一个就出 Bug。

**核心诉求：换 PCB 只改一个文件，每个功能独立成模块。**

---

## 二、重构四步走

| 步骤 | 内容 | 涉及文件 |
|:---:|:---|:---|
| 1 | 引脚宏集中管理 | 新建 `board_config.h`，修改 6 个驱动文件 |
| 2 | 拆分 menu.c | 拆成 5 个独立模块 + 精简 menu.c |
| 3 | 头文件自包含 | 每个 `.h` 包含自己依赖的头文件 |
| 4 | 消除 extern | 每个 `.c` 自给自足，不偷别人的变量 |

---

## 三、知识点详解

### 3.1 引脚集中管理 —— `board_config.h`

#### 问题

重构前，引脚定义散落各处：

```
OLED.c:    GPIO_WriteBit(GPIOB, GPIO_Pin_8, ...)   // PB8=SCL
MyI2C.c:  GPIO_WriteBit(GPIOB, GPIO_Pin_10, ...)  // PB10=SCL
Key.c:    GPIO_ReadInputDataBit(GPIOB, GPIO_Pin_1) // PB1=Key1
LED.c:    GPIO_ResetBits(GPIOC, GPIO_Pin_13)       // PC13=LED
AD.c:     GPIO_Init(GPIOA, ...)                     // PA0=ADC
menu.c:   GPIO_ResetBits(GPIOB, GPIO_Pin_13)       // 关机引脚
```

**换 PCB = 改 6 个文件，风险高。**

#### 解决方案

把所有引脚抽象为有名字的宏，集中到 `board_config.h`：

```c
/* ===== OLED I2C ===== */
#define OLED_I2C_PORT           GPIOB
#define OLED_I2C_SCL_PIN        GPIO_Pin_8
#define OLED_I2C_SDA_PIN        GPIO_Pin_9
#define OLED_I2C_RCC            RCC_APB2Periph_GPIOB

/* ===== 按键 ===== */
#define KEY1_PORT               GPIOB
#define KEY1_PIN                GPIO_Pin_1
#define KEY1_RCC                RCC_APB2Periph_GPIOB
// ...
```

驱动代码改为使用宏：

```c
// 改前
GPIO_WriteBit(GPIOB, GPIO_Pin_8, (BitAction)BitValue);

// 改后
GPIO_WriteBit(OLED_I2C_PORT, OLED_I2C_SCL_PIN, (BitAction)BitValue);
```

**换 PCB 时只需改 `board_config.h` 一个文件。**

#### 关键点

- ADC 的引脚宏和通道宏是两回事：`ADC_GPIO_PIN` 管 GPIO 初始化，`ADC_CHANNEL` 管 `ADC_RegularChannelConfig()`
- `RCC_APB2Periph_ADC1` 是 ADC 外设的时钟使能，和 `ADC1`（外设实例名）是不同的命名空间，需要分别定义宏
- 宏名要见名知义：`OLED_I2C_SCL_PIN` 比 `PIN_OLED_SCL` 好——前缀按功能分区，IDE 自动补全时相关宏排在一起

### 3.2 模块拆分 —— 从大杂烩到独立模块

#### 问题

`menu.c` 里塞了 7 种不相关的功能，前置声明一大堆：

```c
/* 前置声明 — 说明这些函数本该独立 */
void MenuToFunction(void);
int StopWatch(void);
int LED(void);
int MPU6050_Func(void);
// ...
```

#### 拆分原则

**每个功能一个 `.c/.h` 对，用 `app_` 前缀区别于硬件驱动：**

```
重构前：                          重构后：
menu.c (608行)                   menu.c (280行) ← 只剩时钟、设置、菜单
  ├── 秒表相关 ──────────────→   app_stopwatch.c/.h
  ├── 手电筒相关 ────────────→   app_flashlight.c/.h
  ├── MPU6050显示相关 ───────→   app_mpu6050_ui.c/.h
  ├── 表情包相关 ────────────→   app_emoji.c/.h
  └── 水平仪相关 ────────────→   app_gradienter.c/.h
```

另外，`MPU6050_Calculation()`（互补滤波）本质是数据运算，移到了 `HARDWARE/MPU6050.c`：

```c
// HARDWARE/MPU6050.c — 姿态解算属于硬件数据处理层
float Roll, Pitch, Yaw;   // 全局输出，供多个 APP 模块使用

void MPU6050_Calculation(void)
{
    // 陀螺仪积分 → 加速度计反算 → 互补滤波融合
}
```

#### 关键点

- **APP 层 vs HARDWARE 层**：UI 交互放 APP，数据处理放 HARDWARE。`MPU6050_Calculation` 是纯计算，放硬件层，让水平仪和姿态显示两个 APP 都能用
- **static 封装**：每个模块内部的状态变量（如秒表的 `hour/min/sec`、手电筒的 `led_flag`）都声明为 `static`，外部不可见
- **Menu() 调用方式不变**：拆分后 `Menu()` 里的分支逻辑一行没改，只是通过 `#include` 引入各模块

### 3.3 头文件自包含 —— `.c` 只需一个 include

#### 问题

重构初期，新模块编译报错：

```
error: unknown type name 'uint8_t'
```

原因是 `Key.h` 和 `MPU6050.h` 使用了 `uint8_t`/`int16_t` 类型，但它们自己**没有包含 `<stdint.h>` 或 `stm32f10x.h`**，依赖调用方先引入。原来的 `menu.c` 因为 include 顺序碰巧没问题（`menu.h` → `OLED.h` → `<stdint.h>`），但新文件没有这条链。

#### 正确的做法

**让每个 `.h` 自包含**——它用了什么类型，就必须包含对应的头文件：

```c
// Key.h — 改前
#ifndef __KEY_H
#define __KEY_H
void Key_Init(void);
uint8_t Key_GetNum(void);   // uint8_t 哪来的？依赖调用方！
#endif

// Key.h — 改后
#ifndef __KEY_H
#define __KEY_H
#include "stm32f10x.h"      // 自给自足
void Key_Init(void);
uint8_t Key_GetNum(void);
#endif
```

`stm32f10x.h` 有头文件保护（`#ifndef __STM32F10x_H`），重复包含无害。

#### 逐级包含

然后让上级头文件包含下级，形成清晰的依赖链：

```
menu.c        →  menu.h  （只一行）
  menu.h      →  board_config.h, OLED.h, Key.h, MPU6050.h,
                 所有 app_*.h
    Key.h     →  stm32f10x.h
    MPU6050.h →  stm32f10x.h
    app_*.h   →  各自依赖的 Key.h / OLED.h / Delay.h ...
```

**结果：每个 `.c` 文件只需 include 自己的 `.h`，干净利落。**

#### 关键点

- C 语言的头文件应该是"即插即用"的——include 一个头文件不需要考虑之前 include 了什么
- `#include` 本质是文本替换，头文件保护（`#ifndef`）防止同一文件被展开多次
- 标准库头文件（如 `<stdint.h>`）在 STM32 项目中通常被 `stm32f10x.h` 间接包含

### 3.4 消除 extern —— 不做"变量小偷"

#### 问题

重构过程中，把 `KeyNum` 改为 `static` 后，出现了链接错误：

```
Error: L6218E: Undefined symbol KeyNum (referred from settime.o).
Error: L6218E: Undefined symbol pi (referred from dino.o).
```

原来 `SetTime.c` 和 `dino.c` 通过 `extern` 在偷 `menu.c` 里的全局变量：

```c
// SetTime.c
extern uint8_t KeyNum;   // 偷 menu.c 的

// dino.c
extern uint8_t KeyNum;   // 偷 menu.c 的
extern double pi;        // 偷 menu.c 的（后移到 MPU6050.c）
```

这种写法的问题是：**改一个文件可能影响另一个看起来毫无关联的文件**，重构时最容易踩坑。

#### 修复方式

| 变量 | 原位置 | 引用者 | 修复 |
|---|---|---|---|
| `KeyNum` | menu.c | SetTime.c, dino.c | 各文件各自 `static`，互不干扰 |
| `pi` | MPU6050.c | dino.c | dino.c 自己定义 `static const double pi = 3.1415927` |

**SetTime.c** — `extern` 改为自身的 `static`：
```c
// 改前
extern uint8_t KeyNum;

// 改后
static uint8_t KeyNum;   // SetTime.c 自己的，和别人无关
```

**dino.c** — 去掉两个 `extern`，自给自足：
```c
// 改前
extern uint8_t KeyNum;
extern double pi;

// 改后
static const double pi = 3.1415927;
// KeyNum 改为函数内局部变量（只在 Show_Dino 里用到）
```

#### 关键点

- **`extern` 是重构的头号敌人**——它让编译通过、链接才报错，而且出错信息不直观
- `Key_GetNum()` 返回按键值，每个函数自己声明一个 `uint8_t KeyNum` 接收即可，完全不需要跨文件共享
- `pi` 这种数学常数，哪里用到就在哪里 `static const` 定义，几行而已，不值得跨文件引用
- **原则：每个 `.c` 是自给自足的孤岛，接口只通过 `.h` 的函数声明对外暴露**

## 四、重构前后对比

| 指标 | 重构前 | 重构后 |
|---|---|---|
| menu.c 行数 | 608 | 280 |
| 引脚定义的分散文件数 | 6 | **1**（board_config.h） |

## 五、经验总结

1. **早拆比晚拆好**。100 行的文件拆起来轻松，600 行就要仔细对比，1000 行就痛苦了
2. **引脚宏要先做**。集中引脚定义是回报率最高的重构，做完立刻受益，也让后续拆分更安全
3. **头文件自包含是铁律**。每个 `.h` 必须包含自己用到的类型定义，不能依赖 include 顺序
4. **消灭 extern**。让每个 `.c` 成为独立的孤岛，接口只通过 `.h` 的函数声明暴露
5. **重构要有度**。画板之前做到"换 PCB 只改一个文件"就够了，上 RTOS、改状态机框架等硬件定了再说
